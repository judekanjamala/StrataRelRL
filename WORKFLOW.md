# RRL end-to-end workflow: concrete syntax in, verification errors out

This document describes the actual, working, user-facing workflow for the
`RRL` dialect: write a bicommand program in RRL's *concrete* textual syntax
(an ordinary `.rrl.st` file, same as any other Strata DDM dialect gets for
free), and get back verification diagnostics (pass/fail per proof
obligation, with source locations) — either via the standalone `rrl` CLI
in this package, or programmatically via `RRL.verify`.

## 1. The user writes a concrete RRL program

`RRL` is declared with `#dialect ... #end` in `RRL/DDMTransform/Grammar.lean`:

```
dialect RRL;
import Core;

category Bicommand;
op biembed (left : Command, right : Command) : Bicommand => "(" left " | " right ")";
op command_bicommand (b : Bicommand) : Command => b;
```

This gives RRL a real concrete parser/pretty-printer for free. A program
file looks like `RRL/Examples/Swap.rrl.st` (ported from RelRL's
`examples/all_all/swap/prog.rl`):

```
program RRL;

( {
    var a : int := 0;
    var b : int := 0;
    a := 3;
    b := 3;
    assert [left_a_then_b]: a == 3;
    assert [left_a_then_b]: b == 3;
  }; | {
    var a : int := 0;
    var b : int := 0;
    b := 3;
    a := 3;
    assert [right_b_then_a]: a == 3;
    assert [right_b_then_a]: b == 3;
  };
)
```

Note the trailing `;` after each `{ ... }` side (each side is a full Core
`Command`, i.e. `command_block`, whose own grammar rule is `b ";\n"`), and
*no* trailing `;` after the closing `)` (`command_bicommand`'s rule is
just `b`, with no separator of its own).

Parsing this file (`StrataDDM.readStrataText`) produces a generic
`StrataDDM.Program` — dialect-agnostic DDM AST, every node carrying its
`SourceRange` and dialect-declared metadata (e.g. the `[left_a_then_b]`
label).

## 2. `StrataDDM.Program` → `Core.Program` (`RRL.DDMTransform.Translate`)

`RRL/DDMTransform/Translate.lean` is the dialect-owned translator. Like
every other real translator in this codebase (Core's own, C_Simp's,
Laurel's), it hand-walks the raw `Operation`/`Arg` AST directly — **no
dialect in the codebase actually uses the DDM-generated `ofAst` Lean AST
for translation**; it's generated by `#strata_gen` but unused in
practice, so RRL follows the same real pattern instead:

- `translateProgram` walks each top-level `Operation` in
  `p.commands`. An `RRL.command_bicommand`-wrapped `RRL.biembed` is
  lowered by `lowerBicommand`; everything else is ordinary embedded Core
  syntax, delegated straight to Core's own `Core.getProgram` (reused
  unchanged, not reimplemented).
- `lowerBicommand` lowers `biembed left right` to a single Core
  `Statement.block "biembed" [leftStmt, rightStmt] md`: left followed by
  right, as one sequential Core block. Left and right are separate state
  spaces (no shared heap/aliasing is introduced) — matching the design
  decision made during development.
- `lowerCommandOp` recurses through nested `RRL.command_bicommand`s (for
  future relational operators) and, for ordinary Core commands, delegates
  to `translateCoreOp`, which wraps the single `Operation` in a synthetic
  singleton `StrataDDM.Program` and calls `Core.getProgram` — reusing
  Core's real, tested per-statement translation instead of hand-rolling it
  again.
- Source positions are preserved via `Imperative.MetaData.ofSourceRange`,
  so verifier diagnostics trace back to the original RRL source span.

The result is an ordinary `Core.Program` — from here on, RRL is invisible;
everything downstream is exactly Core's pipeline, unmodified.

## 3. Core verification (`RRL.Verify`)

`RRL/Verify.lean` wraps `Strata.Core.verifyProgram` exactly the way Core's
own CLI commands do:

```
def verify (p : StrataDDM.Program) (ictx : Lean.Parser.InputContext := ..)
    (options : Core.VerifyOptions := .default) :
    IO (Core.VCResults × Array Message)
```

Internally: `translateProgram` (step 2) produces `(Core.Program,
translation diagnostics)`, then `Strata.Core.verifyProgram` runs Core's
existing VC-generation and SMT-discharge pipeline unmodified — the same
verifier Core uses for every other Core program.

## 4. Driving it: the standalone `rrl` CLI

No dependency on the separate `Strata-CLI` repo is required. `StrataRRL`
defines its own self-contained `lean_exe` (`RRLMain.lean` + `RRL/Cli.lean`,
built on the shared `Strata.Cli.Framework` from the `Strata` dependency):

```console
$ lake build rrl

# Verify an RRL program directly:
$ ./.lake/build/bin/rrl rrlVerify RRL/Examples/Swap.rrl.st
Swap.rrl.st(36, 4) [left_a_then_b]: ✅ pass
Swap.rrl.st(37, 4) [left_a_then_b]: ✅ pass
Swap.rrl.st(43, 4) [right_b_then_a]: ✅ pass
Swap.rrl.st(44, 4) [right_b_then_a]: ✅ pass
All 4 goals passed.

# Or translate to Core concrete syntax and verify separately with any
# generic Core tool (e.g. the unified `strata verify` from Strata-CLI):
$ ./.lake/build/bin/rrl rrlToCore RRL/Examples/Swap.rrl.st > swap.core.st
$ lake exe strata verify swap.core.st   # from a separate Strata-CLI checkout
```

`rrlVerify` accepts the same `--check-mode`/`--solver`/`--vc-directory`/etc.
flags as the generic `strata verify` command (`Strata.Cli.VerifyOptions`),
and uses the same exit-code scheme (0 = success, 2 = failures found, 3 =
internal error).

## Status

Working end-to-end, verified against `RRL/Examples/Swap.rrl.st`:

- Concrete `.rrl.st` parsing ✅
- `StrataDDM.Program` → `Core.Program` translation (`biembed` → sequential
  Core block) ✅
- Core SMT-backed verification via `Strata.Core.verifyProgram` ✅
- Standalone `rrl rrlVerify` / `rrl rrlToCore` CLI commands ✅

Known simplifications (by design, for now):

- No relational pre/post-conditions (`Agree`, `bimodule`-style specs from
  RelRL) — `left`/`right` are verified independently, not relationally.
- No classes/methods/modules — only plain Core commands on each side of a
  single top-level `biembed`.
- `command_bicommand` nesting (for future relational operators beyond
  `biembed`) is plumbed through `lowerCommandOp` but not yet exercised by
  a second operator.
